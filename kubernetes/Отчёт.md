# Отчёт — домашнее задание 2: Kubernetes/minikube

## Что развёртывается

TaskFlow — full-stack приложение: Blazor WebAssembly frontend в NGINX, ASP.NET Core API, PostgreSQL и отдельный `TaskFlow.DbMigrator`. Все ресурсы разворачиваются в namespace `taskflow` командой `kubectl apply -k kubernetes`.

## Использованные абстракции Kubernetes

| Абстракция | Где использована | Назначение |
|---|---|---|
| `Namespace` | `taskflow` | Изолирует ресурсы приложения от остальных объектов кластера. |
| `StatefulSet` | PostgreSQL | Управляет stateful БД, даёт ей стабильное имя и не выдаёт её за масштабируемый stateless Deployment. |
| `Deployment` | API, frontend | Поддерживает stateless Pod-реплики; API и frontend можно масштабировать командой `kubectl scale`. |
| `Service` | PostgreSQL, API, frontend | Headless Service даёт StatefulSet стабильное DNS-имя `taskflow-postgres`; API получает ClusterIP, frontend опубликован как `NodePort` на 30443. |
| `volumeClaimTemplates` | PostgreSQL StatefulSet | Создаёт независимый PVC `data-taskflow-postgres-0` размером 1 GiB, переживающий перезапуск Pod. |
| `Job` | `taskflow-migrator` | Однократно применяет EF Core migrations. Job ждёт готовности PostgreSQL и допускает до 4 повторов при временной ошибке. |
| `ConfigMap` | PostgreSQL init и NGINX | Передаёт init-скрипты БД и Kubernetes-вариант NGINX-конфигурации без пересборки образов. |
| `Secret` | `taskflow-db-credentials` | Передаёт пароли PostgreSQL как переменные окружения. Значения в учебном манифесте локальные; для реального окружения их нужно заменить. |
| Probes и resources | PostgreSQL, API, frontend, Job | `readinessProbe` исключает неготовый Pod из Service, `livenessProbe` перезапускает зависший контейнер, `startupProbe` даёт время стартовать. У каждого контейнера есть CPU/memory `requests` и `limits`; у API readiness — TCP-проверка 8080, так как `/health/ready` требует аутентификацию. |

## Взаимодействие сервисов

```text
Браузер
  -> NodePort Service taskflow-frontend:30443
  -> Pod frontend: NGINX + Blazor WASM
       -> /api/* same-origin reverse proxy
       -> Service taskflow-api:8080
       -> Pod API (одна или больше реплик)
       -> Service taskflow-postgres:5432
       -> PostgreSQL StatefulSet Pod + PVC data-taskflow-postgres-0

Job taskflow-migrator -> Service taskflow-postgres:5432 (до готовности API)
```

Клиент обращается к `/api/*` через тот же HTTPS-origin. NGINX направляет запросы на `taskflow-api`; Service балансирует их между готовыми API Pod. API и мигратор используют разные роли БД: `taskflow_app` получает DML-права, а `taskflow_migrator` — права на миграции. API не хранит бизнес-состояние в Pod, поэтому его можно масштабировать без sticky sessions: состояние и Data Protection keys находятся в PostgreSQL.

## Как проверить результат

1. Собрать и загрузить образы: Windows — `Build-And-Load.ps1`, macOS/Linux — `build-and-load.sh`.
2. Развернуть: Windows — `Deploy.ps1`, macOS/Linux — `deploy.sh`.
3. Убедиться, что все рабочие Pod имеют `READY` и `STATUS Running`: `kubectl get pods -n taskflow`.
4. Открыть URL, который печатает `minikube service taskflow-frontend -n taskflow --url`. Используется локальный self-signed TLS-сертификат, поэтому браузер покажет стандартное предупреждение.
5. Масштабировать API: `kubectl scale deployment taskflow-api -n taskflow --replicas=3`, затем снова выполнить `kubectl get pods -n taskflow`.
